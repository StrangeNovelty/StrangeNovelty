# ADR-0003: Primary Database and Physical Persistence

## Status

Accepted

- Proposed: 2026-07-11
- Decided: 2026-07-11
- Last amended: —

This ADR establishes PostgreSQL as the primary relational database and the high-level persistence model, while exact version, hosting, schema, stable-ID encoding, indexes, connection settings, backup tooling, retention, replication, RPO, RTO, and monitoring remain undecided.

## Decision Owners

- Decision owner: Strange Novelty repository owner
- Authors: Codex draft prepared for owner review
- Reviewers: repository owner; data architecture, Django, security, privacy, operations, migration, export, backup, and recovery perspectives

## Context

ADR-0001 establishes Strange Novelty as a private authenticated web application whose application server is the primary policy-enforcement boundary. The browser cannot connect directly to the database. Every private operation is authorized against the current owner and Workspace on the server. Jobs, AI, exports, backups, migrations, and restoration retain bounded authority.

ADR-0002 selects Python on a supported CPython runtime with Django as the cohesive web framework. Django application services mediate private reads and durable writes. The application remains a modular monolith initially, with internal boundaries rather than premature services.

The data model is strongly relational. Version 1 must preserve:

- one private Workspace and explicit ownership;
- Worlds, Series, Books, Chapters, Scenes, Characters, and Locations;
- stable identity independent of names and hierarchy;
- Scene revisions and optimistic concurrency;
- typed Links with derived backlinks;
- explicit content states and Creative Context;
- authored, imported, and AI-generated provenance;
- staged imports and AI suggestions;
- recoverable deletion and retained history;
- deterministic migrations;
- useful exports, complete backups, and isolated restoration; and
- privacy-conscious operation.

These requirements involve multi-record transactions, referential integrity, unique and check constraints, indexed relational queries, concurrent requests and jobs, durable append-oriented history, and consistent backup. The primary database therefore needs to optimize for correctness, recoverability, portability, and conservative operation rather than novelty or speculative scale.

The old Story Engine used a local SQLite file accessed directly from a desktop webview. It demonstrated the convenience of one embedded database but also exposed the weaknesses of browser-side database authority, auto-increment-only identity, hard cascade deletion, incomplete provenance, live-file copying, and untested restoration. Strange Novelty must not reproduce that trust or recovery model.

This ADR chooses the database engine and high-level physical-persistence rules. It deliberately does not define the complete schema.

## Decision

If accepted, Strange Novelty Version 1 will use **PostgreSQL as its one authoritative relational database for structured application state**, operated as a database service separate from the browser and accessed only through server-side Django application services and bounded operational processes.

The decision establishes these rules:

1. PostgreSQL is the authoritative structured system of record for Version 1.
2. The browser never connects to PostgreSQL and never receives database credentials.
3. Django application services authorize and scope every private read and durable write by Workspace.
4. Workspace-owned tables carry an explicit `workspace` ownership key by default, even when ownership is also derivable through a parent. Exceptions require a documented invariant and database-enforced parent path.
5. Stable identifiers are generated by the application or an approved server-side mechanism independently of human-readable fields and database row sequence.
6. Database constraints reinforce, but do not replace, application authorization and domain rules.
7. Multi-record authority-changing writes use explicit transaction boundaries.
8. Mutable authoritative records carry a version or equivalent consistency token for optimistic concurrency.
9. Revisions, provenance, state transitions, and required audit history are durable records rather than overwritten history.
10. Links are authoritative relational records; backlinks are derived and rebuildable.
11. Lifecycle state is explicit. Ordinary deletion is recoverable; hard purge is exceptional and protected.
12. Content state and Creative Context are explicit, relationally queryable concepts.
13. Core invariants use structured relational columns and constraints.
14. PostgreSQL JSON capabilities may be used only for bounded extension metadata, source payloads, manifests, provider-independent details, or other justified flexible fields.
15. Ordinary manuscript hierarchy and core authority data are not stored solely as opaque JSON documents.
16. Large binary objects remain outside the primary database if later analysis selects object storage; authoritative metadata, ownership, integrity, lifecycle, and object references remain relational.
17. Search indexes, caches, backlinks, and other derived representations are non-authoritative and rebuildable.
18. Migrations are reviewed, deterministic, forward-tested transformations with recovery points and transformation reporting.
19. Production data is never copied casually into development or CI; tests use synthetic data.
20. Database backups use PostgreSQL-consistent mechanisms rather than arbitrary copying of live files.
21. Logical exports and operational backups are separate artifacts with different purposes.
22. Restoration occurs in isolation and validates representation, constraints, references, counts, object references, and representative application behavior before activation.
23. Database users and service credentials are least-privileged and server-side.
24. Database logs and diagnostics do not routinely contain manuscript bodies, secrets, or raw private request parameters.

The exact PostgreSQL version, host, operating system, process topology, managed or self-hosted form, schema, indexes, identifier encoding, connection settings, backup commands, retention, replication, RPO, RTO, and monitoring products remain later decisions.

## Selected Database Engine

PostgreSQL is recommended because it provides a mature combination of:

- ACID transactions and multiple isolation levels;
- row-level concurrency and explicit locking mechanisms;
- primary keys, foreign keys, uniqueness, checks, exclusion constraints, and deferrable constraints where applicable;
- mature query planning and diverse index types;
- native text-search capabilities sufficient to evaluate for Version 1;
- structured SQL types plus bounded JSON support;
- application-independent logical dumps;
- physical base backups and write-ahead-log-based recovery possibilities;
- least-privilege roles and database-level privileges;
- strong Django integration; and
- open-source, provider-neutral operation across self-hosted and managed environments.

No single feature determines the selection. The fit comes from supporting a normalized, highly connected creative archive and its recovery lifecycle without introducing distributed-database or document-store semantics.

“Separately operated” means PostgreSQL runs as a database service rather than as a file opened by the browser or embedded in the web process. It does not require a separate vendor, machine, container, or network topology; those remain undecided.

## Authoritative Data Boundary

PostgreSQL will hold authoritative structured application state, including:

- Workspace ownership and owner-related application references;
- narrative hierarchy and ordering;
- Scenes and required revision metadata/content according to the later Scene-storage decision;
- Characters and Locations;
- Links and information needed to derive backlinks;
- content states and Creative Context assignments;
- provenance, imports, AI operations, AI suggestions, and authority-changing records;
- lifecycle and recovery state;
- private-object metadata and integrity references;
- export, backup, verification, migration, and restoration metadata where required; and
- bounded job and security records appropriate for database persistence.

The database is not automatically the correct store for:

- large binary artwork, maps, archives, or backup artifacts;
- raw operational logs and high-volume telemetry;
- provider secrets or encryption keys requiring separate secret handling;
- browser caches;
- rebuildable search indexes hosted elsewhere in a later design; or
- external-provider copies.

Where data is stored elsewhere, PostgreSQL retains authoritative ownership, identity, lifecycle, provenance, integrity, and reference metadata. No external object or index becomes the only record of creative meaning.

## Workspace Ownership Strategy

Every Workspace-owned table will carry an explicit Workspace foreign key by default. This includes child records whose ownership could also be inferred through a parent.

The default is chosen because explicit ownership:

- makes authorization filters visible and consistent;
- reduces the chance that a join omission crosses a Workspace boundary;
- supports constraints and indexes that include Workspace;
- enables safer background-job revalidation;
- makes imports, exports, purge, backup, and restoration scopes easier to verify;
- permits detection of parent/child ownership disagreement; and
- leaves room for future multiple Workspaces without changing identity semantics.

Redundant ownership must remain consistent. The schema should use composite uniqueness, foreign-key patterns, controlled application services, or other database-supported constraints where practical so a child cannot name one Workspace while referencing a parent in another.

An exception may omit direct ownership only when:

- the record is truly global and contains no Workspace-private data;
- ownership is enforced through one unambiguous required parent path;
- every query path remains safe and testable; and
- the exception is documented in schema design.

Application authorization still resolves the current owner and Workspace server-side. A Workspace column is not row-level authorization by itself. Database row-security features may be evaluated later as defense in depth but are not selected by this ADR.

## Stable Identity Strategy

Authoritative records use stable opaque identifiers that:

- are generated independently of names, titles, slugs, order numbers, paths, content state, and hierarchy;
- are not database auto-increment sequence values used as the portable identity contract;
- survive rename, reorder, move, archive, deprecation, export, restore, and provider migration;
- are preserved when restoring the same Workspace;
- are never reused after deletion;
- can be referenced safely by revisions, Links, provenance, manifests, and external mappings; and
- can map old Story Engine or future provider identifiers as external provenance.

PostgreSQL supports types suitable for opaque stable IDs, but the exact encoding and generation algorithm remain a later implementation detail or ADR. The decision does not require UUID, ULID, integer, or any specific textual representation.

Database-local surrogate values may exist for internal optimization only if they never replace the stable exported identity and cannot be confused with it.

## Transaction and Consistency Model

Explicit transactions protect coherent multi-record changes such as:

- moving hierarchy records and updating order;
- saving a Scene revision and advancing its current-revision pointer;
- creating or changing Links and invalidating derived backlinks;
- recording a content-state transition, Creative Context, approval, and provenance event;
- applying an approved imported item;
- retaining an AI suggestion and its operation provenance;
- soft deletion or recovery with relationship reconciliation; and
- committing migration or restoration stages.

Application services define transaction boundaries. Views, forms, jobs, and commands call those services rather than composing partial writes independently.

Transactions should be as short as correctness allows. External AI calls, object transfers, export generation, and other slow network work do not occur inside a database transaction. The system records intent, commits it, performs bounded external work, then revalidates before committing results.

The default database isolation behavior and any stronger isolation or explicit locking for particular workflows remain implementation decisions. Code must handle serialization failures, deadlocks, constraint errors, and safe retry where applicable. Retrying never repeats unsafe external effects without idempotency.

Constraints provide final integrity protection within their supported scope. Cross-row creative rules that do not fit sound relational constraints remain explicit application-service invariants with tests; they should not be hidden in fragile triggers or opaque callbacks merely to move logic into the database.

## Concurrency Model

Mutable authoritative records expose a version, revision reference, timestamp-plus-version, or equivalent consistency token. A client or job submits the base token it observed.

A durable update succeeds only when:

- the authenticated owner and Workspace remain authorized;
- the target is in an allowed lifecycle state;
- the submitted base token matches current authoritative state; and
- all domain and constraint checks pass.

The update atomically advances the token. A mismatch produces a visible conflict rather than last-write-wins.

The mechanism applies to concurrent tabs, devices, requests, and jobs. Database transactions and conditional updates reinforce the check. Timestamps alone should not be relied on if their resolution or semantics cannot distinguish writes reliably.

The exact token representation, locking queries, merge UX, and autosave cadence remain later decisions.

## Revision and Provenance Persistence

Scene identity is separate from Scene Revision identity. Revisions are append-oriented durable records. Restoring old content creates a new current revision rather than rewriting or deleting intervening history.

Revision persistence must support:

- stable Scene and revision identifiers;
- Workspace ownership;
- base and predecessor references;
- creation time and initiating actor or process;
- content or a durable content reference;
- save source and concurrency information where useful;
- current-revision selection;
- incomplete-chain detection; and
- export, backup, migration, and restoration.

Provenance is also durable and distinct from current content state. It records authored, imported, and AI-generated origin; source references; review; authority-changing actions; derivation; and significant transitions without storing secrets.

Ordinary edits do not erase origin. Applying an imported or AI result creates the required derivation and review records. Exact revision content representation, diffs, snapshots, retention, and compaction remain undecided.

## Content State and Creative Context Persistence

Content state and Creative Context are explicit relational concepts, not free-form tags buried in manuscript JSON.

Persistence must allow the application to query:

- current and prior state assignments;
- the classified record or content identity;
- Workspace ownership;
- context type and anchor;
- prior and resulting state;
- active, superseded, or deprecated status;
- explicit author approval and provenance event;
- timestamps and optional reason; and
- relevant concurrency version.

Canon is never inferred from table membership, hierarchy, external publication, AI output, import success, or a boolean field without context. Database constraints should enforce valid references, supported state values, and uniqueness of active assignments where the final model defines it. Application services enforce contextual meaning and approval rules.

## Link and Backlink Persistence

Links are authoritative typed relational records with their own stable identity, Workspace, source type and ID, target type and ID, supported kind, optional note, provenance, timestamps, and lifecycle status.

The persistence model must prevent:

- cross-Workspace endpoints;
- missing endpoints;
- unsupported type/kind combinations;
- name-based identity;
- accidental duplicate active Links where uniqueness rules prohibit them; and
- silent cascade loss of linked creative records.

Polymorphic endpoint implementation details require careful schema design and remain a later decision. Database constraints should be used where they can express endpoint integrity without flattening all domain records into one generic table.

Backlinks are the reverse query of authoritative Links. They may be queried directly or materialized as derived data. If materialized, they are rebuildable, invalidated or updated within a documented boundary, checked for disagreement, and never authoritative over Links.

## Lifecycle and Deletion Persistence

Lifecycle is explicit and separate from creative state.

Version 1 persistence distinguishes:

- active;
- archived;
- deprecated as a creative state where applicable;
- soft-deleted or trashed;
- restored; and
- permanently purged.

Ordinary deletion sets recoverable lifecycle state and records the action. It does not automatically cascade hard deletion through hierarchy, Links, revisions, provenance, imports, or AI records.

Database foreign-key actions default toward restricting or preserving related records rather than broad destructive cascades. A cascade may be used only where the child has no independent meaning, recovery need, or audit value and the behavior is documented and tested.

Permanent purge is a separate explicit workflow that inventories children, Links, revisions, provenance, objects, staged operations, and backup retention. Identifiers are not reused. Existing backups may retain purged material until their normal expiry.

Exact trash retention, purge scheduling, archival fields, and lifecycle event schema remain later decisions.

## Relational and Flexible Data

Core invariants use typed relational columns and relationships. This includes identity, Workspace, hierarchy, order, record type, content state, Creative Context, lifecycle, provenance references, revisions, Links, concurrency, and timestamps.

PostgreSQL JSON or equivalent flexible columns are permitted only when flexibility is justified and bounded, such as:

- original imported source payloads retained under an approved policy;
- import transformation warnings or unmapped fields;
- context manifests;
- provider-independent request or result metadata;
- format-specific export metadata;
- bounded extension attributes not yet authoritative domain fields; and
- diagnostic structured details that comply with privacy rules.

Flexible fields must have:

- an owning record and Workspace where applicable;
- a documented schema or version expectation;
- size and depth limits;
- validation at the application boundary;
- explicit privacy and retention behavior;
- migration rules when their meaning changes; and
- indexes only when demonstrated queries justify them.

JSON is not an escape from schema design. Manuscript hierarchy, stable IDs, Links, state, contextual Canon, provenance, revisions, and lifecycle cannot exist solely inside opaque documents.

## Search and Derived Data

PostgreSQL’s text-search and indexing capabilities are sufficient to evaluate as the initial Version 1 search implementation for Scenes, Characters, and Locations. This ADR does not finalize search configuration, ranking, language processing, or index design.

Search rules remain:

- every query is authorized and Workspace-scoped;
- searchable fields follow the data-model document;
- result identity uses stable IDs;
- content state, Creative Context, origin, and lifecycle can filter results;
- search terms and snippets are private;
- indexes are rebuildable from authoritative records;
- index lag, if any, is bounded and detectable; and
- no search representation becomes the sole copy of content.

PostgreSQL indexes may support hierarchy, ownership, uniqueness, state, links, revisions, and text search. Exact indexes follow observed queries and query-plan evidence; speculative indexing is avoided.

External search engines, vector databases, embeddings, semantic search, caches, and materialized views are not selected. They require later evidence and remain derived systems.

## Django Integration Boundary

Django’s database backend, ORM, migrations, and transaction APIs are the default application integration boundary for PostgreSQL.

Rules include:

- views, forms, jobs, and commands call application services rather than issue ad hoc authoritative writes;
- query services apply Workspace scoping centrally and visibly;
- transactions surround coherent domain operations;
- conditional updates or locks enforce concurrency where required;
- ORM models preserve typed domain distinctions;
- raw SQL is exceptional, parameterized, reviewed, tested, and isolated behind a clear interface;
- database-specific capabilities are used deliberately and documented when they affect portability;
- migration files are reviewed as executable data transformations; and
- provider-specific connection or hosting metadata does not enter domain records.

Django ORM support does not replace database design, query analysis, constraints, or operational backup. It also does not make authorization automatic.

The exact model definitions, managers, repositories, connection pooling, transaction settings, and database driver versions are outside this ADR.

## Database Roles and Access

Database access follows least privilege. Expected logical roles include:

- **application runtime** — normal authorized reads and writes required by application services, without database administration or backup authority;
- **migration operator** — schema and reviewed data-migration authority enabled only through protected deployment workflows;
- **backup operator** — authority required for a consistent backup, without ordinary application mutation rights where practical;
- **restoration operator** — authority limited to an isolated restoration target until activation;
- **read-only diagnosis** — optional bounded metadata/query access for approved operational investigation; and
- **database administrator** — exceptional infrastructure authority, separately protected and audited.

Logical roles may map differently depending on deployment, but privilege separation remains the goal.

Credentials:

- remain server-side and outside Git;
- differ by environment and role;
- are not embedded in browser assets, exports, logs, or provenance;
- are rotated and revocable;
- use protected transport and authentication appropriate to deployment; and
- do not grant provider staff or future integrations application authority.

Database ownership or administrative access does not imply authorial approval. Administrative writes must not silently alter Canon, provenance, or audit history.

## Migration Model

Database migrations are version-controlled, reviewed transformations executed through a protected server-side operational workflow.

Every material migration should define:

- source and target representation;
- preconditions and supported starting versions;
- stable-ID, Workspace, state, context, Link, revision, provenance, and lifecycle preservation;
- handling of invalid or incomplete data;
- deterministic transformation rules where practical;
- expected counts and integrity checks;
- failure, retry, resume, and rollback or restore behavior;
- privacy-conscious transformation reporting;
- representative synthetic fixtures; and
- a verified recovery point before execution.

Schema migration and application deployment order must support safe compatibility during the chosen deployment process. Destructive field or table removal is delayed until data preservation, export, backup compatibility, and rollback needs are resolved.

Django migrations are the expected mechanism for application schema evolution, but generated migration code still requires human review. Custom data migrations must not hide story-specific assumptions or silently change creative meaning.

The old Story Engine is never migrated in place. A later importer reads an approved copy or export into staged Imported content through application services.

## Backup Model

Operational backups protect restoration of the running application. They differ from logical author-facing exports.

PostgreSQL supports multiple consistent backup approaches, including logical dumps and physical/base-backup methods; write-ahead-log archiving can support point-in-time recovery. This ADR selects none of those exact mechanisms, but requires the chosen backup design to use database-supported consistency rather than arbitrary copying of live database files.

A complete Strange Novelty backup must coordinate:

- authoritative database state;
- required private objects;
- schema and application representation versions;
- migration state;
- manifest and integrity evidence;
- required encryption/key recovery information under the later security design;
- backup creation and verification status; and
- references needed to test restoration.

Backup credentials are separate from application credentials where practical. Backups exclude live sessions, provider tokens, database credentials, and secret-bearing configuration unless a later explicitly approved recovery design protects required key material separately.

Backup existence is not verification. Verification checks readability, expected components, integrity, object references, and supported versions. A restoration test remains distinct.

Exact commands, tooling, destinations, schedules, retention, replication, RPO, RTO, and encryption products remain later decisions.

## Restoration Model

Restoration occurs in an isolated or deliberately prepared environment, never through ordinary application CRUD or direct replacement of a live database file.

The restoration workflow must:

1. authenticate and authorize the recovery operator;
2. validate backup identity, format, version, manifest, and integrity;
3. provision an isolated target without exposing it publicly;
4. restore PostgreSQL using a supported consistent method;
5. restore or reconcile required private objects;
6. apply supported deterministic migrations;
7. validate schema version and migration state;
8. validate constraints, Workspace ownership, parent references, stable IDs, Link endpoints, revision chains, state/context assignments, lifecycle records, and provenance;
9. compare expected record groups and bounded counts from the manifest;
10. verify private-object presence and integrity references;
11. rebuild or verify backlinks, search indexes, and other derived data;
12. keep restored sessions, credentials, integrations, callbacks, and queued jobs inactive;
13. run representative authenticated application checks; and
14. require explicit review before activation.

Failure leaves the existing archive intact or follows a tested rollback path. Restoration is not proven until representative hierarchy, Scene content and revisions, Characters, Locations, Links, states, contexts, provenance, lifecycle, and objects are usable.

## Development and Test Data

- Production databases, replicas, dumps, exports, backups, manuscripts, artwork, prompts, and private objects are never copied casually into development, CI, demos, or issue attachments.
- Development and automated tests use synthetic data designed to exercise representative structure without imitating private story content.
- Migration fixtures include edge cases such as duplicate names, missing optional fields, invalid parent references, stale versions, conflicting states, and incomplete operations.
- Test databases use separate credentials and are disposable.
- Test identifiers and timestamps are deterministic where useful without becoming production assumptions.
- Performance tests use generated data with documented shapes and volumes.
- Debugging production-only failures begins with metadata, bounded reproduction, and synthetic fixtures rather than copying private rows.
- Any exceptional protected production-data access follows the administrative and incident-response rules.

Local development may use a developer-operated PostgreSQL instance or another provider-neutral environment. SQLite may be useful for isolated unit tests that do not claim backend equivalence, but database integration and migration tests must run against PostgreSQL because backend behavior is part of this decision.

## Operational and Privacy Boundaries

Operational database practices must preserve manuscript privacy:

- statement, slow-query, audit, and error logging are configured to avoid routine SQL parameter values and manuscript bodies;
- query text is reviewed for whether it embeds sensitive literals;
- diagnostic dumps, query samples, traces, and support bundles are private artifacts;
- database metrics prefer counts, timings, locks, storage, and health rather than row contents;
- database names, role names, hostnames, and identifiers avoid unnecessary story information;
- crash dumps and core files receive sensitive-data handling;
- production debug access is exceptional and auditable;
- patching and support lifecycle are monitored; and
- database availability failure does not trigger fallback to an unprotected local file or browser store.

Operational errors returned to the browser never expose connection strings, SQL, schema internals, credentials, private values, or provider details.

Observability products and logging configuration remain later choices.

## Rationale

PostgreSQL is the best fit because Strange Novelty’s core is not an unstructured document collection. It is a connected archive whose meaning depends on typed identity, Workspace ownership, hierarchy, Links, revisions, states, Creative Context, provenance, lifecycle, and authority-changing transactions.

The strongest reasons are:

1. **Relational integrity matches the domain.** Foreign keys, uniqueness, checks, and deferrable constraints can reinforce the relationships the data model already requires.
2. **Concurrent server workflows need mature transactions.** Interactive writes, multiple tabs, jobs, imports, AI results, and recovery operations benefit from row-level concurrency, conditional updates, locking, and explicit transaction control.
3. **Django support is first-class.** Django’s ORM, migrations, transactions, testing, and PostgreSQL-specific capabilities can serve the cohesive modular monolith without a separate data platform.
4. **Structured data and bounded flexibility coexist.** Core invariants remain relational while JSON and text-search types can support carefully bounded metadata and Version 1 search without changing the system of record.
5. **Recovery and provider exit have mature paths.** Logical dumps, physical backup, write-ahead-log recovery possibilities, open tooling, and broad hosting options support verified backup, isolated restoration, and provider independence.

PostgreSQL is not selected for speculative scale. A single-owner application may have modest traffic. It is selected because correctness and recovery matter more than request volume.

## Alternatives Considered

### Alternative: PostgreSQL as a separately operated relational database

PostgreSQL provides strong relational constraints, transactions, concurrent access, indexing, text search, bounded JSON, Django integration, role-based privileges, logical export, physical backup, and point-in-time recovery possibilities.

It is the recommendation. Its main disadvantage is operational responsibility: a server database must be deployed, patched, monitored, backed up, and restored. It is more infrastructure than an embedded file for a single owner. That cost is accepted in principle because the application is already a private server-side web application with concurrent requests and jobs, and because recovery correctness is a core product property.

### Alternative: SQLite as the primary production database

SQLite is simple, portable, transactional, mature, and easy to operate. It can be an excellent choice for low-write applications and local tools. It supports foreign keys when enabled and can support concurrent readers, with one writer at a time.

It is not selected because Strange Novelty is a server application with interactive saves, multiple tabs or devices, and background jobs. Serialized writes, file-level operational concerns, runtime-specific constraint settings, schema-alteration limitations, and backup coordination create avoidable risk. Using SQLite would also repeat too much of the old Story Engine’s file-centric operational model, even if the new application correctly mediated access.

SQLite remains appropriate for isolated tools or tests only when they do not claim production-backend equivalence.

### Alternative: MySQL or MariaDB with a transactional storage engine

MySQL and MariaDB with a transactional engine support ACID transactions, row-level locking, foreign keys, indexes, replication, backup tooling, mature operations, and Django. They can satisfy the primary architecture.

They are not selected because PostgreSQL offers a more uniform fit for the anticipated combination of constraints, deferrable relational integrity, text search, rich SQL types, bounded JSON, and Django-specific capabilities. MySQL/MariaDB require careful attention to engine, SQL mode, collation, and product-specific behavioral differences. These are manageable, but no compensating advantage is evident for Version 1.

They remain credible fallback choices if owner operations expertise or deployment constraints strongly favor them.

### Alternative: document-oriented database as the primary system of record

A document database can store evolving records and imported payloads flexibly, align with JSON APIs, and reduce joins for aggregate documents. Some document engines provide schema validation and multi-document transactions.

It is not selected because Strange Novelty’s core invariants cross many records: hierarchy, Workspace ownership, Links, backlinks, revisions, state assignments, Creative Context, provenance, and lifecycle. Modeling these as nested or duplicated documents would either weaken relational integrity or require application-managed consistency and more complex multi-document transactions. Flexible metadata is useful, but it should not replace typed core relationships.

### Alternative: hosted backend database exposed directly to browser clients

A browser-accessible backend service can provide authentication integration, generated APIs, realtime updates, storage, and reduced server code. Provider policy features may restrict rows.

It is rejected because ADR-0001 explicitly prohibits direct browser database access. It would distribute authorization into client code and provider policy, expose a larger data API, complicate application-service invariants, and risk making the hosting product authoritative or difficult to replace. Provider row policies may be defense in depth later, never the primary application boundary.

### Alternative: defer the database choice and begin implementation

Deferral could preserve flexibility and allow early UI work before physical persistence is settled.

It is not selected because identity, constraints, migrations, concurrency, transactions, search, backup, and restoration materially shape the first vertical slice. Beginning with a provisional database risks allowing development convenience to become an undocumented durable choice and makes representative integration tests impossible. UI exploration may use disposable synthetic prototypes, but application implementation should not depend on an undecided system of record.

## Evidence

## Consequences

### Positive

- Strong relational integrity reinforces the data model.
- Mature transactions and concurrency support interactive writes and jobs.
- Django integration is first-class and well tested.
- Stable identity and append-oriented history fit naturally.
- Content states, Creative Context, Links, and provenance remain queryable.
- Bounded JSON supports source metadata without flattening core records.
- Native text search may satisfy Version 1 without another service.
- Logical and physical recovery options support different recovery needs.
- Broad self-hosted and managed options preserve provider choice.
- One authoritative database avoids distributed consistency complexity.

### Negative

- PostgreSQL must be deployed, patched, monitored, backed up, and restored.
- It adds a network/service dependency compared with an embedded database.
- Correct connection, transaction, lock, and migration handling requires operational discipline.
- Backup and point-in-time recovery capabilities are not automatic; they must be configured and tested.
- PostgreSQL-specific features can increase migration cost if used indiscriminately.
- Explicit Workspace columns create controlled redundancy that must be constrained.
- Append-oriented history and soft deletion increase storage and query complexity.

### Neutral or Operational

- Low traffic does not remove the need for a correct database.
- A managed provider may later reduce operations but does not change the engine decision.
- A self-hosted database may share infrastructure with the application while remaining a separate service boundary.
- Search can begin inside PostgreSQL and move to a derived service later if evidence requires it.
- Private objects may use a different store later, with relational metadata retained here.

## Risks and Mitigations

| Risk | Impact | Mitigation | Residual risk |
| --- | --- | --- | --- |
| Operational burden exceeds solo-owner capacity | Missed patches, failed backups, or downtime | Prefer boring supported deployment, automate verified procedures later, document recovery, consider managed hosting in a separate ADR | Database operations remain a real responsibility |
| Workspace filter omitted in an application query | Cross-Workspace data exposure | Explicit Workspace columns, scoped query services, composite constraints, authorization tests, possible later database defense in depth | Application bugs remain possible |
| Redundant Workspace ownership becomes inconsistent | Corrupt authorization scope | Database-enforced parent/Workspace relationships where practical, service-layer validation, integrity checks | Some polymorphic relationships may be difficult to constrain completely |
| Long or incorrectly scoped transactions | Locks, contention, or failed saves | Short application-service transactions, no external calls inside transactions, query/lock diagnostics, retry rules | Complex operations may still contend |
| Optimistic concurrency implemented inconsistently | Silent overwrite | Shared service pattern, conditional updates, version constraints, request/job tests, conflict UX | Bulk and migration paths need separate care |
| JSON becomes an unreviewed schema escape hatch | Hidden invariants and hard migrations | Bounded approved uses, validation, versioning, size limits, schema review | Flexible payloads still accumulate migration obligations |
| Soft deletion and history complicate queries | Incorrect visibility or storage growth | Central lifecycle filters, explicit purge workflow, indexes based on measured queries, retention decisions later | Historical volume grows over time |
| Database-specific features create lock-in | Harder migration to another engine | Use features only for documented value, keep exports engine-neutral, isolate specialized queries, test restoration | Full engine migration would still be substantial |
| Backup is configured but not restorable | False confidence and data loss | Manifest verification, isolated restoration tests, representative checks, separate recovery copies | Rare corruption modes can remain undetected |
| Database logs expose manuscript text | Privacy breach | Parameter/log controls, bounded diagnostics, no body logging, access limits, privacy tests | Emergency diagnosis may still require carefully controlled content access |
| Search queries reveal private terms operationally | Metadata leakage | Avoid routine parameter logging, protect query diagnostics, keep search server-side | Authorized administrators may retain technical access |
| Stable-ID choice made casually later | Export or merge problems | Separate implementation decision, portability tests, never use names or row sequence | Every encoding has tradeoffs |

## Security and Privacy Review

- Security-sensitive: Yes
- Primary references: `docs/architecture/security.md`, ADR-0001, and ADR-0002
- Additional references: `docs/architecture/data-model.md`, `docs/architecture/ai-context.md`, and `docs/architecture/integrations.md`

### Protected assets

PostgreSQL will hold or reference most protected structured assets: manuscripts, revisions, story entities, Links, content states, contextual Canon, provenance, import and AI records, lifecycle history, object metadata, audit records, and recovery metadata.

### Trust boundaries

The database is inside the private application infrastructure boundary but outside the browser. Access crosses authenticated server-to-database, migration, backup, restoration, and exceptional administrative paths. Each path requires distinct least privilege.

### Access and credentials

- No database port or credential is exposed to the browser.
- Runtime, migration, backup, restoration, and administration roles are separated where practical.
- Credentials remain outside Git and client-visible configuration.
- Production and non-production credentials differ.
- Protected transport and server authentication are configured according to the later deployment design.
- Future integrations and AI providers receive no database access.

### Data minimization and logging

Database logs, traces, query samples, error reports, dumps, and support artifacts must minimize private content. Routine statement logging with bound values or manuscript-bearing SQL is prohibited. Operational access is bounded and audited.

### Backup and restoration security

Backups inherit the database’s sensitivity and may contain the complete archive. They require protected storage, integrity, encryption decisions, least-privilege access, retention, and secure disposal. Restoration must not activate credentials, sessions, integrations, jobs, or unvalidated content.

### Required security testing

- database network inaccessibility from the browser and public network;
- least-privilege role capabilities;
- cross-Workspace query and relationship attempts;
- constraint and transaction failure behavior;
- stale-write and job revalidation;
- injection resistance and parameterized queries;
- error redaction and database-log configuration;
- secret exclusion from Git, exports, and routine backups;
- backup authorization and integrity;
- isolated restoration with malformed, incomplete, or incompatible artifacts;
- production-data exclusion from development and CI; and
- administrative-access auditability.

### Residual risk

A compromised application runtime or sufficiently privileged database operator can access private data required for processing. Database encryption at rest does not prevent authorized runtime access. Hosting, encryption, key custody, and administrator exposure remain later security decisions.

## Product and Architecture Alignment

### Product alignment

The decision prioritizes trustworthy storage, explicit creative authority, recovery, portability, and author ownership. It supports a private workspace without requiring enterprise scale or external custodianship.

### Scope alignment

One PostgreSQL database supports Version 1’s hierarchy, Scenes, Characters, Locations, Links, states, provenance, search, export, backup, and restoration. It does not add future entities, collaboration, public sharing, integrations, semantic search, or publishing.

### ADR alignment

The decision preserves ADR-0001 by keeping the browser untrusted, database access server-side, credentials private, jobs bounded, and recovery isolated. It preserves ADR-0002 by using Django’s supported relational integration and a cohesive modular monolith.

### Architecture alignment

It preserves:

- explicit Workspace ownership;
- stable identity independent of names and row sequence;
- typed records rather than a generic document graph;
- optimistic concurrency and revisions;
- relational Links and derived backlinks;
- explicit states and Creative Context;
- durable provenance and lifecycle;
- narrow AI and integration boundaries;
- documented export and complete backup; and
- deterministic migration and tested restoration.

### Normative-document impact

No product or architecture document requires amendment for this Proposed ADR. If accepted, the ADR index should be updated. Physical schema and operational decisions must remain consistent with it or explicitly supersede it.

## Migration, Portability, and Recovery

### Old Story Engine migration

The old SQLite database is a possible future import source, never a database to upgrade in place or attach directly to production. A future importer will:

- read an approved copy or structured export;
- detect source schema version;
- exclude settings and credentials;
- validate size, structure, and references;
- create an Import Batch;
- map old numeric IDs as external provenance;
- generate stable Strange Novelty IDs;
- assign Workspace ownership and Imported content state;
- report duplicates, transformations, unmapped fields, and partial failures; and
- require explicit author review.

No old content becomes Canon automatically.

### Database portability

Portability is supported through:

- provider-neutral PostgreSQL use;
- documented schema migrations;
- engine-neutral author-facing exports;
- stable application IDs;
- provider-independent provenance and object references;
- limited and documented PostgreSQL-specific features;
- logical dump capability for operations; and
- restoration tests outside the live environment.

Migration to a different engine would still require deliberate transformation and testing. Open SQL and export formats reduce, but do not eliminate, that cost.

### Recovery

Recovery requires both database-consistent backup and required private objects. Point-in-time capability may later reduce loss after operational mistakes, but it does not replace revision history, soft deletion, logical export, or representative restoration tests.

The live provider is never the sole recovery path. Backup interpretation information, migrations, source, dependency metadata, and restoration procedures remain under the owner’s control.
