# ADR-0004: Stable Identifiers, Revisions, and Optimistic Concurrency

## Status

Accepted

- Proposed: 2026-07-11
- Decided: 2026-07-11
- Last amended: —

This ADR establishes the Version 1 stable-identifier, Scene revision, optimistic-concurrency, conflict, and idempotency model, while complete Django models, PostgreSQL schema, Scene content encoding, API routes, editor technology, rejected-draft storage, and job infrastructure remain undecided.

## Decision Owners

- Decision owner: Strange Novelty repository owner
- Authors: Codex draft prepared for owner review
- Reviewers: repository owner; domain, data, Django, PostgreSQL, security, editor, export, migration, backup, and recovery perspectives

## Context

Strange Novelty must preserve creative work through rename, reordering, hierarchy moves, multiple tabs, delayed jobs, imports, AI operations, exports, backups, restoration, migrations, and provider changes. Names and hierarchy are editable. Database row location and sequence are physical details. Neither can serve as durable creative identity.

ADR-0001 places all authoritative reads and writes behind server-side application services. The browser is untrusted, IDs convey no authority, and jobs must revalidate current state before committing.

ADR-0002 selects Python/CPython and Django. Django application services mediate authorization, validation, transactions, and persistence.

ADR-0003 selects PostgreSQL and establishes:

- explicit Workspace ownership;
- application-generated stable identifiers;
- explicit transactions for multi-record writes;
- optimistic concurrency on mutable authoritative records;
- append-oriented revisions and provenance;
- stable identity independent of names and row sequence; and
- preservation across export, restoration, and migration.

The conceptual data model already distinguishes Scene identity from Scene Revision identity. It prohibits silent last-write-wins and requires restoration of old content as a new current revision. This ADR makes those requirements implementable without defining the complete schema or editor format.

The old Story Engine used database-generated integer IDs, updated current Chapter rows in place, and added selective full-draft snapshots. Those snapshots demonstrate useful recovery intent, but the old model did not provide portable identity, a complete revision lineage, or consistent stale-write detection. Old numeric IDs may later be retained only as external import provenance.

The decision must distinguish several concepts that are easily conflated:

- application identity from physical row location;
- identity from names, slugs, URLs, and hierarchy;
- Scene identity from Scene Revision identity;
- revision lineage from operational audit history;
- provenance from revision lineage;
- concurrency tokens from authentication and authorization;
- browser draft state from committed revisions;
- session undo from durable restoration;
- restoring content from mutating history;
- detecting a conflict from resolving one;
- idempotent retry from permission to act;
- revision history from database backup; and
- source-system identity from Strange Novelty identity.

## Decision

If accepted, Version 1 will use the following model.

### Stable identity

1. Every authoritative record receives one stable opaque application identifier.
2. The preferred identifier is an application-generated UUID version 7 conforming to RFC 9562, provided the selected supported Python/PostgreSQL implementation can generate and validate it reliably.
3. If that support is unavailable, insufficiently mature, or operationally unclear when implementation begins, the application uses cryptographically random UUID version 4 without changing the architectural model.
4. No database sequence, title, name, slug, URL, order number, timestamp alone, or hierarchy-derived value is the portable identity contract.
5. Identifiers are generated by trusted server-side code before authoritative persistence, are immutable, are never reused, and are preserved when restoring the same archive.
6. Imported records receive new Strange Novelty IDs. Source identifiers are stored separately as provenance mappings.

### Revision model

1. Scene is the durable creative identity.
2. Scene Revision is an immutable durable representation of one committed Scene version and has its own stable ID.
3. Version 1 stores an append-oriented complete Scene snapshot for every committed revision.
4. A mutable Scene record points to exactly one current revision after the Scene has committed content and carries a monotonically increasing integer version.
5. Prior revision content is never mutated when the current revision advances.
6. Restoring an earlier revision creates a new revision with restoration lineage and advances the Scene through the ordinary concurrency transaction.

### Optimistic concurrency

1. The client receives a consistency token containing the Scene integer version and current-revision ID, or an equivalent pair with the same semantics.
2. A save submits both observed values.
3. The application service authenticates, authorizes, Workspace-scopes, validates, and reloads current Scene state inside an explicit transaction.
4. The service creates the new immutable revision and advances the Scene current-revision pointer and version only if both submitted values still match.
5. Revision creation and Scene advancement are one atomic transaction.
6. On success, the Scene version advances monotonically.
7. On mismatch, no authoritative content is overwritten and no committed orphan revision is left as the result of that failed save.

### Conflict behavior

1. Version 1 never silently uses last-write-wins.
2. Version 1 performs no automatic semantic or text merge.
3. An authorized conflict response identifies the base revision, current revision, and current version and provides enough current content or comparison context for recovery without overexposing data.
4. The submitted stale draft is preserved long enough for the authorized owner to compare, copy, reload, retry deliberately against current state, or abandon it.
5. A future force-replace operation, if approved, requires current reauthorization, the newest token, explicit author intent, a new revision, and provenance.

### Idempotency

1. Retryable requests and jobs use a Workspace-scoped operation ID or idempotency key where ambiguous failure could create duplicate durable effects.
2. Reuse with materially different normalized input is rejected.
3. Idempotency never bypasses authentication, authorization, Workspace scoping, validation, concurrency, or current-state revalidation.
4. Provider-side effects require their own reconciliation and are never repeated blindly.
5. Exact idempotency storage, retention, expiry, and archival are later implementation details.

## Stable Identifier Strategy

The portable application identifier is a 128-bit UUID value conforming to the current UUID standard.

UUIDv7 is preferred because it combines globally unique-enough generation with time ordering that generally improves index locality and operational sorting compared with uniformly random UUIDv4. Its time component is not trusted as the authoritative creation timestamp, security evidence, or ordering guarantee across records.

UUIDv4 is the conservative fallback because it is mature, widely supported, simple to generate securely, and does not require clock-based monotonic behavior. Falling back changes neither field semantics nor export contracts: both are UUID values stored and serialized through standard representations.

The choice between preferred and fallback must be made before the first authoritative record is created. Version 1 does not mix algorithms casually. If both versions must later coexist, records remain distinguishable as UUIDs and validation must allow the documented set without changing identity.

Every authoritative type uses stable application identity, including:

- Workspace;
- World, Series, Book, Chapter, and Scene;
- Scene Revision;
- Character and Location;
- Link;
- state/context assignment and provenance records where independently referenced;
- Import Batch and retained staged item;
- AI operation and retained AI suggestion;
- export, backup, migration, restoration, audit, and job records where durable cross-reference requires it.

The exact set of records requiring first-class IDs is finalized in physical schema design, but no authoritative creative record relies only on database row sequence.

## Identifier Generation and Validation

Identifiers are generated server-side by the application or an approved trusted server mechanism before insertion.

Generation requirements:

- conform to RFC 9562 for the selected UUID version;
- use a maintained implementation available in the selected supported runtime or a separately reviewed dependency;
- use cryptographically suitable randomness where the algorithm requires it;
- define behavior under clock rollback, same-millisecond generation, process concurrency, and restarts for UUIDv7;
- never incorporate manuscript content, user names, device identifiers, MAC addresses, provider IDs, hierarchy, or secrets;
- fail closed if reliable generation is unavailable; and
- be covered by collision, format, version, concurrency, serialization, import, and restoration tests.

Validation requirements:

- parse into a canonical UUID value rather than compare unvalidated strings;
- accept only documented UUID versions for newly generated records;
- preserve valid identifiers during restoration of the same archive;
- reject malformed, nil, unsupported, or duplicate identifiers where policy requires;
- never silently regenerate an ID to make an invalid restoration succeed; and
- report source and target ID mappings during import or migration.

PostgreSQL’s native UUID type is the expected physical storage family and Django’s UUID field support is the expected framework representation, but exact column declarations and text/binary serialization remain schema details.

Application-generated means identity exists before dependent records are assembled and does not depend on one database instance. Database defaults may later reinforce trusted generation, but a database-only sequence cannot become the portable contract.

## Identifier Exposure and Authorization

Stable IDs may appear in URLs, forms, API-like payloads, job references, export manifests, and logs where a bounded reference is necessary. A URL is a locator, not identity itself; route shape may change while record identity remains stable.

An ID exposed to the browser:

- is not a secret;
- conveys no permission;
- does not prove Workspace ownership;
- must be parsed and reauthorized server-side on every operation;
- must not reveal private record existence through differing unauthorized responses; and
- must not be accepted as a substitute for a current consistency token.

Time ordering in UUIDv7 can reveal approximate generation time. The application must not describe UUIDs as unguessable access tokens or privacy boundaries. If approximate creation-time disclosure in public-facing contexts becomes unacceptable, opaque mapping or route design may be considered without changing record identity. Version 1 has no public sharing.

Operational logs should avoid unnecessary stable IDs when a short-lived correlation ID is sufficient. Audit and provenance records may require stable references but still exclude manuscript bodies.

## Imported and External Identifiers

Source identifiers are evidence of origin, not Strange Novelty identity.

For each imported record, the import system stores a bounded mapping that may include:

- Import Batch;
- source type and format version;
- safe source description;
- source record type;
- source identifier as an opaque value;
- assigned Strange Novelty stable ID;
- source parent or relationship identifiers where needed for mapping;
- transformation and duplicate-review status; and
- timestamps and author disposition.

An Old Story Engine integer ID is retained only in such provenance. It is not used as a PostgreSQL primary identity, exposed as proof of authority, or assumed unique outside its source database/table scope.

Importing into a Workspace creates new Strange Novelty IDs unless the operation is explicitly validated as restoration of that same Workspace/archive. Re-import does not automatically generate duplicates or merge by name; source mapping and author review determine handling.

External integration/provider IDs follow the same rule. Provider changes do not change Strange Novelty identity.

## Scene and Scene Revision Identity

A Scene represents the enduring narrative unit through title changes, hierarchy moves, content revisions, archive, soft deletion, export, and restoration.

A Scene Revision represents one immutable committed content state of one Scene. It cannot move to another Scene or Workspace.

Each revision records, conceptually:

- its own stable ID;
- Workspace ID;
- Scene ID;
- predecessor revision ID where applicable;
- base revision ID observed by the initiating operation;
- restoration source revision ID when created by restoration;
- creation time;
- initiating authenticated owner or bounded process;
- save source, such as interactive save, approved import application, AI-derived author action, or restoration;
- committed Scene content in the later selected encoding;
- required content metadata such as a deterministic size or integrity value where later justified;
- provenance references; and
- operation/idempotency reference where relevant.

Revision identity is not a revision number alone. A display sequence may be derived for the author, but it is not portable identity.

The mutable Scene record holds narrative metadata, hierarchy, lifecycle, current-revision reference, and integer version. It does not overwrite the immutable content of prior revisions.

## Revision Representation

Version 1 uses append-only full Scene snapshots for committed revisions.

Full snapshots are selected because they provide:

- simple retrieval of any revision;
- straightforward validation and integrity checking;
- independent export and restoration;
- easier migration across content encodings;
- failure isolation from a broken delta chain;
- understandable author recovery;
- simpler tests; and
- lower implementation risk for a single-owner Version 1 workload.

The snapshot contains the complete authoritative Scene content in the selected content encoding. That encoding—plain text, structured rich text, Markdown, or another representation—remains a separate decision.

Storage overhead is accepted provisionally. Representative evidence must be gathered before considering deltas or compaction. If full snapshots become unacceptable, a later ADR may introduce a compatible representation while preserving immutable revision identity, reconstructability, provenance, export, and restoration.

Operational autosave pings, cursor positions, transient editor state, and formatting caches do not each require a committed revision unless the later editor workflow explicitly defines them as acknowledged saves.

## Revision Lineage

Revision lineage explains content ancestry. It is not the same as provenance or audit.

- **Predecessor lineage** identifies the previously current revision from which the new committed revision advances.
- **Base lineage** identifies the revision the editor or job actually observed. For an ordinary successful save, base and predecessor should normally be the same.
- **Restoration lineage** identifies an older revision whose content was intentionally restored into a newly created revision.
- **Derivation provenance** identifies imported, AI-generated, copied, or otherwise derived sources and author review.
- **Operational audit** records security-sensitive events and operation outcomes without duplicating the revision content.

Version 1 expects one current linear committed history per Scene. Conflicting stale submissions do not create competing authoritative branches automatically. The rejected submission may be retained temporarily for conflict recovery, but it is not a committed Scene Revision until the owner deliberately saves it against current state.

The design must detect missing predecessors, cross-Scene lineage, cross-Workspace lineage, cycles, invalid current pointers, and revisions unreachable from expected history. Exact database constraints and validation queries remain schema work.

## Current Revision Selection

A Scene with committed content points to exactly one current Scene Revision belonging to the same Scene and Workspace.

The current pointer:

- is authoritative for ordinary reads;
- advances only through an authorized transaction;
- is accompanied by the monotonically increasing Scene version;
- is never inferred from maximum timestamp, UUID order, revision count, or database insertion order;
- does not delete or mutate the previous current revision; and
- is preserved in export and restoration.

A newly created empty Scene may have no current revision until its first successful content save, or may begin with an explicit empty initial revision. The choice remains a schema/editor detail, but every state must be unambiguous.

Derived display order may use committed creation time and lineage. UUIDv7 order is not the authority for current selection.

## Optimistic Concurrency Model

The consistency token for a mutable Scene is the pair:

- Scene integer version; and
- current Scene Revision stable ID, or explicit null for a permitted never-committed Scene.

The pair detects both metadata/current-pointer changes and ambiguity about the content base. The integer advances monotonically on every authoritative Scene mutation that could affect an editor’s safe save assumptions. The precise set of mutations that advance it must be consistent and documented.

The token is not:

- authentication;
- authorization;
- a bearer secret;
- a CSRF defense;
- a stable record ID;
- a replacement for transaction isolation; or
- proof that submitted content is valid.

Timestamps are retained for human understanding and provenance but are not sufficient consistency tokens. Clock precision, skew, equal timestamps, and formatting conversions make them unsuitable as the sole comparison.

Database transaction IDs and PostgreSQL system columns are not selected as portable application tokens because they are physical/database lifecycle details and do not belong in exports or cross-provider contracts.

## Save Transaction

An interactive Scene save follows this conceptual transaction:

1. The browser submits Scene ID, observed Scene version, observed current-revision ID, proposed content, and an operation ID where retry ambiguity is possible.
2. The Django application service validates the current authenticated session and CSRF/request protections.
3. It authorizes the owner and Workspace against authoritative server state.
4. It validates the Scene ID, proposed content, request size, operation ID, and supported save intent.
5. It begins a PostgreSQL transaction.
6. It loads or conditionally targets the current Scene row inside the transaction.
7. It verifies Workspace, lifecycle, permissions, integer version, and current-revision ID.
8. It validates domain rules and any associated provenance or state effects.
9. It generates a stable ID for the new Scene Revision.
10. It inserts the immutable full revision with predecessor/base lineage and required provenance.
11. It conditionally advances the Scene current-revision pointer and increments the version only if the submitted token still matches.
12. It records required audit or operation status without manuscript bodies in operational logs.
13. It commits the transaction.
14. It returns the new revision ID, new Scene version, and bounded current metadata.

Implementation may perform the conditional check before revision insertion or use another transaction-safe ordering, but a failed match must not leave a revision represented as a successful committed save or advance the Scene.

If a uniqueness, constraint, serialization, or deadlock error occurs, the service rolls back and returns a safe failure. Automatic retries are permitted only when the operation is idempotent and current state is revalidated.

External AI calls, imports from providers, object transfers, and other slow work occur outside this transaction. Their results later attempt an ordinary authorized save or create a separate suggestion/staged record.

## Conflict Detection

A conflict is detected when the submitted consistency token no longer equals the authoritative Scene token or when current lifecycle/domain state makes the proposed write unsafe.

Relevant cases include:

- another tab saved a revision;
- another device saved a revision;
- a background job committed an authorized Scene change;
- the Scene was moved, archived, soft-deleted, restored, or otherwise changed in a way included in its version semantics;
- a delayed request arrived after a newer save;
- a retry has different input or operation identity; or
- the base revision is missing, invalid, or belongs to another Scene/Workspace.

Conflict detection occurs server-side inside the save transaction. Browser comparison may predict a conflict for usability but is not authoritative.

Pessimistic locks may be used briefly inside the transaction to implement a conditional update safely, but the product does not lock a Scene for the duration of an editing session. Long-lived edit locks would be fragile across browser crashes, network loss, and multiple devices.

Detection does not choose whose content is correct. It only prevents silent overwrite and provides facts for explicit resolution.

## Conflict Response and Recovery UX

On conflict, the server returns a dedicated conflict outcome rather than a generic success or silent retry.

For the authenticated, authorized owner, the response or follow-up comparison flow should provide:

- Scene stable ID;
- submitted base version and revision ID;
- current version and revision ID;
- bounded current revision metadata;
- current content or a protected way to load it for comparison;
- preservation/reference of the rejected submitted content;
- explanation that no authoritative overwrite occurred; and
- available deliberate next actions.

Version 1 actions include:

- copy all or part of the stale draft;
- reload the current revision;
- compare current and submitted content;
- abandon the stale draft;
- edit the current revision and submit a new save with the latest token; or
- deliberately replace current content after review, if a force-replace workflow is later approved.

There is no automatic semantic merge, three-way text merge, or last-write-wins in Version 1. The system may provide a textual comparison without claiming that it can resolve creative meaning.

Rejected content must be preserved long enough to survive the conflict screen and common refresh/retry mistakes. Exact server-side versus browser-side storage, retention time, encryption, and cleanup remain part of the editor/conflict implementation decision. It must not enter routine logs, analytics, error reports, or URLs.

A later force-replace operation must use the latest token, create a new immutable revision, preserve the overridden current revision, record explicit author intent and provenance, and still satisfy authorization and lifecycle rules.

## Browser Draft and Autosave Boundary

Browser-local editing state is untrusted and non-authoritative.

The browser may retain transient draft text to support responsive editing and recovery, but:

- local state does not advance the Scene version;
- local state is not a committed revision;
- a “saved” indication appears only after server commit acknowledgment;
- autosave uses the same authorization, validation, token, transaction, and conflict rules as an explicit save;
- browser storage is never the sole copy of acknowledged content;
- local drafts do not become Canon, provenance, or audit events merely by existing;
- local drafts are protected according to shared-device and sensitive-cache risks; and
- refresh, tab close, offline behavior, quota failure, and cleanup are communicated honestly.

The browser-local storage technology and autosave cadence are not selected. Version 1 may begin with explicit save if that is safer for the first milestone.

Editing-session undo is also separate. Undo may manipulate local editor state before save. Durable revision restoration creates a new committed revision after authorization and concurrency checks.

## Job and Command Concurrency

Background jobs and management commands use the same application services and concurrency rules as interactive requests unless a separately documented maintenance workflow justifies a narrower exception.

A Scene-affecting job records:

- Workspace and Scene IDs;
- observed Scene version and current-revision ID;
- bounded task and source references;
- initiating operation and authority;
- expected output type;
- idempotency/retry identity; and
- expiration or cancellation rules.

Before commit, the job:

1. authenticates its service identity;
2. reauthorizes the supported operation;
3. reloads Workspace, Scene, lifecycle, version, and current revision;
4. revalidates sources and domain rules;
5. refuses or creates a conflict when state changed; and
6. commits through the same atomic revision/pointer transaction if an authoritative save is permitted.

AI review normally creates an AI Suggestion rather than a Scene Revision. Applying it is a later explicit owner action against the latest Scene token.

Maintenance commands do not receive implicit power to bypass history or concurrency. Exceptional repair procedures must be documented, protected, audited, verified, and preserve enough evidence to explain the repair.

## Idempotency and Retry

Idempotency protects against duplicate effects after timeouts, lost responses, job redelivery, process restart, or uncertain commit outcomes. It does not authorize an operation.

Where duplicate durable effects are possible, the caller or server assigns a stable operation ID/idempotency key. The retained idempotency record is conceptually:

- Workspace-scoped;
- bound to operation type and authenticated/service actor;
- bound to a normalized input fingerprint that excludes secrets while safely detecting material input changes;
- associated with target record IDs and relevant base token;
- assigned a bounded state such as received, in progress, committed, failed, outcome unknown, or expired;
- linked to the resulting revision or other durable effect when successful; and
- retained or archived under a later policy.

Behavior:

- first valid use executes normally;
- same key and same material input returns or reconciles the prior result rather than duplicate it;
- same key with different material input is rejected;
- expired keys follow a documented policy rather than silently appearing new;
- authorization and current state are checked on every attempt;
- a previously authorized key does not grant future permission; and
- sensitive manuscript bodies are not copied into idempotency records merely to fingerprint them.

For a Scene save, idempotency complements the version/current-revision token. It can distinguish a duplicate delivery of the already committed save from a new stale save.

External provider calls require separate effect handling. If the provider lacks reliable idempotency and the outcome is unknown, the system reconciles or asks for deliberate retry rather than blindly repeating a billable, publishing, messaging, or destructive action.

Exact key format, hashing, database representation, uniqueness constraints, retention, expiry, and cleanup remain later details.

## Deletion, Restoration, and History

Stable identity and history survive normal lifecycle changes.

- Archiving or soft deletion does not change Scene or revision IDs.
- Moving a Scene does not change identity or lineage.
- Soft deletion preserves current-revision pointer, revisions, provenance, Links needed for recovery, and lifecycle events.
- Recovering a soft-deleted Scene restores the same Scene identity and validates its current revision and relationships.
- Restoring content from an older revision creates a new revision; it does not move the current pointer backward without recording a new commit.
- Prior revisions remain immutable and navigable according to authorization and lifecycle policy.
- Revision deletion or compaction is prohibited by default.
- Permanent purge is a separately authorized lifecycle operation that addresses all revisions, provenance, Links, imports, AI records, and backup retention.
- Stable IDs are never reused after purge.

Revision history is not a database backup. It can recover prior Scene content but cannot reconstruct all hierarchy, entities, Links, credentials, objects, or database state after system loss.

Backup restoration is not revision restoration. It reconstructs the archive in isolation and preserves the current pointer and all retained revisions as of the recovery point.

## Export, Import, Backup, and Recovery

### Export

Documented exports preserve:

- Workspace and record stable IDs;
- Scene and Scene Revision IDs;
- the current-revision reference and Scene version where useful for re-import/analysis;
- revision lineage and documented revision scope;
- content encoding/version;
- provenance and content-state references;
- lifecycle status; and
- format version and integrity metadata.

Human-readable names accompany IDs but never replace them. Exported IDs confer no access if later presented to the application.

### Import

Ordinary import creates new Strange Novelty IDs and records source IDs separately. It must not overwrite or merge merely because a source ID, name, or content matches. Re-import uses explicit source mappings and conflict review.

Identity-preserving import is reserved for validated restoration or a separately approved same-archive transfer. It must prove Workspace/archive identity and reject collisions or mixed archives.

### Backup

Backups preserve exact IDs, Scene versions, current-revision pointers, immutable revisions, lineage, provenance, idempotency/operation records required for consistency, and schema/version metadata. A backup is broader than revision history.

### Restoration

Isolated restoration validates:

- UUID format, allowed versions, uniqueness, and Workspace ownership;
- Scene/current-revision consistency;
- revision-to-Scene ownership;
- predecessor/base/restoration lineage;
- missing revisions, cycles, and cross-Workspace references;
- version and pointer coherence;
- idempotency references required to explain committed effects;
- expected record counts and integrity data; and
- representative application behavior.

Restoration preserves identity for the same archive. It does not regenerate IDs or rewrite lineage to hide damage. Invalid artifacts fail visibly.

### Provider and hosting migration

Because identity is application-generated and stored in standard UUID form, moving PostgreSQL hosting, Django deployment, object storage, AI provider, or future integrations does not change record identity. Provider IDs remain external mappings.

## Django and PostgreSQL Boundary

Django application services own the authoritative workflow. PostgreSQL supplies atomicity, constraints, conditional updates, and durable storage.

Expected boundary behavior:

- Django parses and validates UUID values through supported framework types;
- PostgreSQL stores them using its native UUID type or an equivalent standard representation selected in schema design;
- the application service opens the transaction and performs authorization/domain validation;
- a conditional update compares both Scene version and current-revision ID;
- database uniqueness and foreign keys reinforce revision identity and ownership;
- transaction rollback prevents partial pointer/revision commits;
- operation uniqueness reinforces idempotency; and
- constraint failures are translated into privacy-conscious domain outcomes.

The full model definitions, indexes, foreign-key form, deferrability, locking statement, SQL, and transaction isolation remain implementation details.

PostgreSQL system columns, physical tuple identity, sequence values, and transaction IDs are not exported application identity or concurrency contracts.

Django model `save()` convenience must not permit an unguarded Scene overwrite. Important writes go through explicit services that require the expected token.

## Rationale

The combined model favors correctness and recoverability with the smallest understandable Version 1 mechanism.

The strongest reasons are:

1. **Portable identity is independent of infrastructure.** Standard UUIDs survive database, hosting, export, restore, and provider changes without coordination with one sequence generator.
2. **UUIDv7 improves locality without changing semantics.** It offers time-ordered generation under a published standard, while UUIDv4 provides a mature fallback with the same UUID contract.
3. **Full snapshots make history dependable.** Every committed revision can be read, exported, validated, and restored independently without reconstructing a patch chain.
4. **A version-plus-revision token detects stale writes clearly.** The integer tracks mutable Scene state while the revision ID proves the exact content base.
5. **One atomic save preserves integrity.** Revision creation and current-pointer advancement either both commit or neither becomes an authoritative save.

The model avoids event sourcing, automatic merge, database-specific temporal history, and delta chains because Version 1 does not need their complexity.

## Decision Criteria

The alternatives were evaluated against:

- global uniqueness sufficient for portable archives;
- generation without a central database sequence;
- standardization and cross-language/database support;
- index locality and operational diagnosis;
- privacy leakage;
- immutability and non-reuse;
- preservation across export, restore, merge analysis, and migration;
- Django and PostgreSQL support;
- simple complete revision retrieval;
- integrity under missing/corrupt records;
- storage and write amplification;
- editor-save latency;
- concurrency across tabs, devices, jobs, and retries;
- explicit conflict detection;
- author recovery from stale drafts;
- idempotency under ambiguous outcomes;
- migration away from the chosen representation;
- backup and isolated restoration validation; and
- implementation and maintenance burden for one owner.

Fashion, lexicographic aesthetics, URL length, and theoretical distributed scale are not deciding criteria.

## Alternatives Considered

### Stable-ID alternative: random UUID version 4

UUIDv4 is standardized, mature, cryptographically random when generated correctly, widely supported, and independent of clocks and databases. It is the fallback and would be an acceptable primary choice.

It is not preferred because uniformly random insertion can provide poorer index locality than time-ordered UUIDv7. At Version 1 scale this may be minor, so implementation reliability takes priority: uncertainty about UUIDv7 support triggers the v4 fallback.

### Stable-ID alternative: time-ordered UUID and UUID version 7

UUIDv7 is standardized by RFC 9562, encodes Unix-epoch milliseconds plus randomness/monotonic behavior, remains a normal UUID, and generally sorts by generation time.

It is preferred conditionally. Its risks are dependence on reliable implementation, clock behavior, and approximate timestamp disclosure. The time field is never treated as authoritative creation time or permission.

### Stable-ID alternative: ULID

ULID offers compact, lexicographically sortable text and broad library availability. It is not selected because UUIDv7 now provides standardized time-ordered UUID semantics with native PostgreSQL UUID storage and framework interoperability. ULID would add a separate encoding and validation contract without a demonstrated Version 1 benefit.

### Stable-ID alternative: database-generated integer sequences

Sequences are compact, efficient, and simple within one database. They are not selected as portable identity because uniqueness depends on a database/sequence scope, merge and re-import need remapping, and old-system experience shows how easily internal row numbers become external identity.

An internal surrogate integer may be considered only if hidden behind and never confused with the stable UUID, but this adds dual-key complexity and is not recommended without measured need.

### Stable-ID alternative: human-readable or path-derived identifiers

Names, titles, slugs, and paths are convenient in URLs and debugging. They are not selected because they change, collide, reveal private content, and couple identity to hierarchy and language. They may be derived locators only.

### Stable-ID alternative: hierarchy-derived composite identifiers

Composite paths can express location and enforce parent scope. They are not selected because moves and reordering would change identity, cross-cutting Links become fragile, and exports/restoration must rewrite references.

### Stable-ID alternative: internal database key plus portable application ID

Dual identifiers can optimize joins while preserving portable identity. They are not selected by default because PostgreSQL supports native UUID keys and a second key adds constraints, mapping, debugging, and accidental-exposure risks. It remains an optimization only if representative evidence demonstrates a need.

### Revision alternative: append-only full Scene snapshots

Every committed revision stores complete content. This is selected for Version 1 because it is simplest to reason about, retrieve, verify, export, migrate, and restore.

The cost is storage and write amplification. This is acceptable until representative evidence proves otherwise.

### Revision alternative: append-only deltas or patches

Deltas reduce repeated content storage and may improve write size. They are not selected because retrieval and restoration depend on an intact ordered chain, corruption has wider impact, patch semantics depend on content format, and migrations/exports become more complex.

### Revision alternative: periodic snapshots plus deltas

This balances storage with bounded reconstruction. It is not selected because it adds compaction cadence, chain validation, snapshot selection, and migration complexity before storage evidence requires it.

### Revision alternative: in-place Scene updates with a separate audit log

This reduces content duplication and can record who changed what. It is not selected because audit is not guaranteed to reconstruct exact prior content, current writes can destroy recoverable state, and restoration becomes dependent on log completeness.

### Revision alternative: event sourcing as primary persistence

Event sourcing can preserve all transitions and rebuild state. It is not selected because it turns every domain change into event-schema infrastructure, complicates projections, migrations, queries, privacy deletion, and restoration, and exceeds Version 1 needs. The product requires trustworthy history, not a complete event-sourced system.

### Revision alternative: database-native temporal/history features

Temporal facilities can automate row history. They are not selected because portability and Django integration vary, application creative revisions need explicit meaning and provenance, and database history is not the same as author-visible revision lineage.

### Revision alternative: defer representation until editor implementation

Deferral could align storage with the final content format. It is not selected because the first vertical slice materially depends on identity, save atomicity, conflict behavior, export, backup, and restoration. The content encoding remains deferred; full-snapshot semantics do not.

### Concurrency alternative: integer version counter

An integer is simple, monotonic, and suitable for conditional updates. Alone, it does not prove which content base the editor saw. It is selected as part of the pair, not alone.

### Concurrency alternative: current-revision ID token

The revision ID precisely identifies the content base. Alone, it may not capture metadata/lifecycle changes relevant to safe saving. It is selected as part of the pair.

### Concurrency alternative: timestamps

Timestamps are useful metadata but insufficient alone because of precision, clock, equality, conversion, and semantic ambiguity. They are rejected as the consistency token.

### Concurrency alternative: database transaction IDs or system columns

Physical database values can detect some changes efficiently. They are rejected as the portable application contract because they can wrap, change across dump/restore, expose database internals, and do not express Scene revision meaning.

### Concurrency alternative: pessimistic editing locks

Long-lived locks can prevent concurrent edits but are fragile across tabs, devices, crashes, and network loss. They are rejected for editing sessions. Short database locks inside the save transaction remain an implementation tool.

### Concurrency alternative: automatic last-write-wins

Rejected because it silently destroys acknowledged work and conflicts with product and data-model invariants.

### Concurrency alternative: browser-only conflict detection

Rejected because the browser is untrusted and cannot observe all devices, jobs, commands, or current database state.

### Concurrency alternative: mutable version plus immutable revision identity

This is selected. It combines simple monotonic mutation tracking with an exact content-base reference and supports atomic conditional saves.

## Evidence

### Repository evidence

- Product principles require stable ownership, transparency, reversibility, and recovery.
- The Version 1 scope requires drafting, revision, and recovery from editing mistakes.
- The data model explicitly separates Scene and Scene Revision, requires concurrency tokens, prohibits last-write-wins, and requires restoration as a new revision.
- The security architecture keeps browser values untrusted and requires reauthorization of every write.
- ADR-0001 requires server-side writes and job revalidation.
- ADR-0002 establishes Django application services as the write boundary.
- ADR-0003 establishes PostgreSQL, application-generated stable identity, explicit transactions, optimistic concurrency, append-oriented history, and isolated restoration.
- The old Story Engine audit documents local integer IDs, in-place current updates, and selective snapshots without complete concurrency or revision lineage.

## Consequences

### Positive

- Identity survives infrastructure and hierarchy changes.
- IDs can be generated before transactions and used across dependent records.
- UUIDv7 improves likely index locality; UUIDv4 preserves a safe fallback.
- Every committed Scene state is independently readable.
- Revision restoration is simple and history-preserving.
- Stale writes cannot silently overwrite acknowledged content.
- Conflict facts are explicit and recoverable.
- Jobs and retries use the same authoritative rules.
- Export and restoration can validate lineage without database sequence assumptions.
- The design remains independent of editor and content format.

### Negative

- UUIDs are larger and less human-friendly than integers.
- UUIDv7 leaks approximate generation time and depends on reliable clock-aware generation.
- Full snapshots duplicate Scene content and increase storage, backup, and write volume.
- The mutable Scene pointer plus immutable revisions requires multi-record transactional logic.
- Conflict UX is more work than last-write-wins.
- Preserving rejected content creates a sensitive temporary-retention obligation.
- Idempotency records add state, cleanup, and privacy considerations.
- Version semantics must remain consistent across all Scene mutations.

### Neutral or Operational

- Revision creation time remains a separate authoritative field even with UUIDv7.
- UUID order does not select the current revision.
- Database backups remain necessary.
- Browser undo and autosave remain editor decisions.
- Automatic merge and revision compaction remain future possibilities requiring separate decisions.

## Risks and Mitigations

| Risk | Impact | Mitigation | Residual risk |
| --- | --- | --- | --- |
| UUIDv7 implementation is immature or unavailable | Collisions, invalid ordering, or dependency risk | Gate on supported reliable implementation; test generation; fall back to standard UUIDv4 | UUIDv4 has poorer index locality but preserves correctness |
| UUIDv7 timestamp leaks creation timing | Sensitive metadata disclosure | Treat IDs as opaque, no public sharing, minimize logs/URLs where possible, allow v4 fallback if risk is unacceptable | Authorized recipients can still inspect embedded time |
| Clock rollback or concurrent generation breaks monotonic expectations | Unexpected ordering or collision risk | Use standards-compliant generator with documented rollback/concurrency behavior; never rely on order for authority | Operational ordering may still not equal commit order |
| Full snapshots grow storage and backups | Higher cost and slower operations | Measure representative workloads; compress at storage layer only if transparent; later compaction ADR with invariants | Long manuscripts and frequent saves can accumulate significantly |
| Incorrect token advancement permits overwrite | Lost work | Shared save service, conditional update, transaction tests, prohibit direct Scene writes | Maintenance paths remain a risk |
| Revision inserted but pointer update fails | Orphan or misleading history | One transaction, rollback on mismatch, constraints and reconciliation checks | Exceptional database failures require verification |
| Conflict draft is lost | Author loses unsaved work | Preserve submitted content through protected conflict flow, clear status, copy/download option if later approved | Browser crash before submission remains outside committed history |
| Conflict draft retention leaks content | Privacy exposure | Short bounded retention, authorization, encryption/storage policy, no logs/URLs, cleanup tests | Any retained duplicate increases exposure |
| Idempotency key reused with changed input | Wrong result returned or duplicate effect | Bind to normalized fingerprint and actor/Workspace; reject mismatch | Canonicalization errors can cause false matches |
| Idempotency mistaken for authorization | Stale permission reused | Reauthorize and revalidate every attempt; keys convey no authority | Implementation mistakes remain possible |
| Force replace bypasses review | Silent loss of current content | Not in V1 by default; if added require latest token, explicit action, new revision, provenance | User can still deliberately choose replacement |
| Lineage corruption appears during restoration | Missing or misleading history | Constraint checks, cycle detection, counts, representative restoration, fail visibly | Some semantic provenance errors may remain undetectable |

## Security and Privacy Review

- Security-sensitive: Yes
- Primary references: `docs/architecture/security.md`, ADR-0001, ADR-0002, and ADR-0003
- Additional references: `docs/architecture/data-model.md` and `docs/architecture/ai-context.md`

### Assets and trust boundaries

The decision governs identifiers, manuscript revisions, conflict drafts, provenance, operation records, export manifests, backups, and restored history. Browser IDs and tokens cross the untrusted-client boundary and are revalidated server-side.

### Authorization

Stable IDs, revision IDs, version counters, and idempotency keys are not credentials. Every request and retry reauthenticates the current session as applicable, reauthorizes the owner/Workspace operation, and validates target ownership. Unauthorized responses do not confirm private record existence.

### Private content

Full revisions and rejected conflict drafts contain manuscript content. They remain inside the protected content boundary, are excluded from routine logs and telemetry, and follow retention, backup, export, and deletion rules. Conflict responses return content only to the authorized owner.

### Integrity

PostgreSQL transactions, uniqueness, foreign keys, conditional updates, and version checks reinforce integrity. Application services enforce domain meaning. No browser, provider, or job can advance a Scene pointer without the ordinary server-side transaction.

### Prompt and provider boundary

AI calls occur outside Scene save transactions. AI results remain AI Suggestions. Applying one requires explicit owner action using the latest Scene token and creates a revision only after all normal checks.

### Required security testing

- malformed, unsupported, nil, duplicate, and cross-Workspace IDs;
- altered IDs in routes, forms, and job payloads;
- UUIDv7 clock rollback and concurrency behavior or verified UUIDv4 fallback;
- unauthorized current revision and history access;
- stale saves across tabs, devices, jobs, and retries;
- atomic rollback after revision insertion or pointer-update failure;
- idempotency key input mismatch and cross-Workspace reuse;
- conflict response minimization and rejected-content retention/cleanup;
- absence of manuscript bodies and tokens from logs, traces, URLs, and errors;
- export/import identity mapping;
- backup and isolated restoration lineage validation; and
- maintenance command inability to bypass authorization and history silently.

### Residual risk

The application server and database must process plaintext revisions. Authorized users can copy IDs and content. UUID uniqueness is probabilistic. Full snapshots increase the amount of sensitive duplicate content retained. These risks are accepted only with server-side controls, tested generation, protected storage, and explicit retention decisions.

## Product and Architecture Alignment

### Product alignment

The decision protects authorial control, prevents silent overwrite, makes important changes reviewable, preserves history, supports recovery, and keeps the author’s archive portable.

### Scope alignment

It supports Version 1 Scene drafting, revision, multiple tabs/devices, export, backup, and restoration without adding collaboration, automatic merge, event sourcing, or advanced history features.

### ADR alignment

- ADR-0001: all IDs and tokens are untrusted in the browser; saves and jobs are server-authorized.
- ADR-0002: Django application services own the save workflow.
- ADR-0003: PostgreSQL provides UUID storage, transactions, constraints, and durable append-oriented records.

### Architecture alignment

The decision preserves stable identity, explicit Workspace ownership, separate Scene/Revision identity, provenance, contextual state, recoverable lifecycle, deterministic migration, derived backlinks/search, and isolated restoration.

### Normative-document impact

No product or architecture document requires amendment for this Proposed ADR. If accepted, the ADR index should be updated. The later content-format and schema decisions must comply with it or explicitly supersede it.

## Migration and Portability

### Old Story Engine

Old numeric table IDs remain external provenance scoped by source database/table/export. Import creates new Strange Novelty UUIDs and explicit mapping records. Duplicate names do not merge identities automatically.

Old Chapter snapshots may be candidate imported content, but they do not automatically become a valid Scene revision chain. A future importer must establish ordering evidence, parent Scene mapping, origin, source timestamp reliability, and author review. Missing lineage remains reported rather than invented.

### Export and re-import

Exports serialize UUIDs in a documented standard form and preserve type, Workspace/archive identity, current pointers, versions, lineage, and provenance. Re-import into a different Workspace creates new identities unless a separately approved merge model exists. Restoration of the same archive preserves them.

### Framework and database migration

The identity and revision semantics are independent of Django model internals and PostgreSQL tuple/transaction identity. Another framework or relational engine can store the same UUIDs, full revisions, pointers, versions, and lineage after a tested migration.

### Representation migration

If Scene content encoding changes, each revision retains or declares the encoding/version needed to interpret it. Migration may transform representation but cannot silently rewrite lineage, origin, or creative meaning. Original or migrated forms follow a later retention decision and verified recovery plan.
